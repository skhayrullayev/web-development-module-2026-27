01Title

Opening · Ochilish

I want to start with a question that sounds trivial. You type an address into your browser and press Enter. What actually happens? Most of you use the web for several hours every day. Almost nobody can describe those two seconds in detail. By the end of this lecture, you will be able to.

02Road map

Bugungi reja

Here is where we are going. Three parts. In the first we look at what web development actually covers, and we follow one request from your keyboard to the screen — that is the backbone of everything else.

In the second part we take that request apart: the verbs, the answers the server gives back, the headers nobody reads until something breaks, and what the padlock in your address bar does and does not promise.

In the third part we pick up the tools — how to read a network, and how to set up the environment you will use until December. We finish with eight questions, and I want you to answer them honestly rather than correctly.

Bugungi yo'nalishimiz. Uch qism. Birinchisida veb-dasturlash nimalarni qamrab olishini ko'rib chiqamiz va bitta so'rovni klaviaturangizdan ekrangizgacha kuzatamiz — bu qolgan hamma narsaning asosi.

06Page vs app

Sahifa va ilova farqi

Here is a distinction that decides the whole shape of this module. A page is a document that already exists. The server hands over a file that was written before you asked for it, and the conversation ends. Your first HTML file next week is a page.

An application decides what to send at the moment you ask. It reads a database, checks who you are, and assembles a response that nobody had written down before. The student portal is an application. Your coursework is an application.

That is why we spend six weeks in the browser and six weeks on the server. You cannot build the second kind until you can build the first kind properly.

Mana shu farq butun modulning shaklini belgilaydi. Sahifa — bu allaqachon mavjud hujjat. Server siz so'rashingizdan oldin yozilgan faylni beradi va suhbat shu bilan tugaydi. Kelasi haftadagi birinchi HTML faylingiz — sahifa.

Ilova esa siz so'ragan paytda nima yuborishni hal qiladi. U ma'lumotlar bazasini o'qiydi, sizning kimligingizni tekshiradi va ilgari hech kim yozib qo'ymagan javobni yig'adi. Talabalar portali — ilova. Sizning kurs ishingiz ham ilova.

Shuning uchun oltita haftani brauzerda, oltitasini serverda o'tkazamiz. Birinchi turdagi narsani yaxshi qura olmasdan, ikkinchisini qurib bo'lmaydi.

07Tracer

Enter bosilganda nima bo'ladi

This is the slide I asked you to remember. I am going to send one request — GET to udea.uz slash courses — and we are going to watch it travel.

[Press Send request. Let it run to the end without commentary.] Six stages, about a third of a second. Now let us do it again slowly.

[Press Reset, then Step.] Stage one, DNS. The browser has a name and needs a number. It asks a resolver and gets back an address: 203.0.113.24. Stop here for a moment. The browser now knows where to go. Tell me — what does it still not know?

[Wait. Accept answers.] It does not know whether anything is listening there. A correct address with a dead server looks exactly the same at this point.

[Step.] Stage two, TCP. Three packets — SYN, SYN-ACK, ACK — and now there is a connection. Stage three, TLS: the server presents a certificate, the browser verifies it against the roots in your operating system, and both sides agree on a key. Only now, thirty milliseconds in, can the actual request be sent.

[Step twice more.] Stage four is the request itself — three milliseconds, the cheapest part of the whole journey. Stage five, the response: two hundred OK, fourteen kilobytes of HTML. Stage six, render: the browser parses that HTML, discovers it needs CSS, JavaScript and images, and fires off more requests. Three hundred and forty-four milliseconds, and the page is usable.

Bu — esda saqlashingizni so'ragan slayd. Men bitta so'rov yuboraman — udea.uz slash courses manziliga GET — va uning sayohatini kuzatamiz.

[Send request bosing. Izohsiz oxirigacha yuring.] Olti bosqich, taxminan sekundning uchdan biri. Endi sekinroq takrorlaymiz.

[Reset, keyin Step.] Birinchi bosqich, DNS. Brauzerda nom bor, unga raqam kerak. U resolverdan so'raydi va manzilni oladi: 203.0.113.24. Shu yerda bir lahza to'xtaymiz. Brauzer endi qayerga borishni biladi. Ayting-chi — u hali nimani bilmaydi?

[Kuting. Javoblarni qabul qiling.] U o'sha manzilda umuman kimdir tinglayaptimi-yo'qmi, bilmaydi. To'g'ri manzil va o'chgan server bu bosqichda aynan bir xil ko'rinadi.

[Step.] Ikkinchi bosqich, TCP. Uchta paket — SYN, SYN-ACK, ACK — va ulanish hosil bo'ldi. Uchinchi bosqich, TLS: server sertifikatini taqdim etadi, brauzer uni operatsion tizimingizdagi ildiz sertifikatlar bilan tekshiradi, ikki tomon kalit bo'yicha kelishadi. Faqat shundan keyin, o'ttiz millisekund o'tib, haqiqiy so'rov yuborilishi mumkin.

[Yana ikki marta Step.] To'rtinchi bosqich — so'rovning o'zi, uch millisekund, butun sayohatning eng arzon qismi. Beshinchi — javob: 200 OK, o'n to'rt kilobayt HTML. Oltinchi — render: brauzer HTML'ni tahlil qiladi, unga CSS, JavaScript va rasmlar kerakligini aniqlaydi va yana so'rovlar yuboradi. Uch yuz qirq to'rt millisekund, va sahifa ishlashga tayyor.

08Failures

Olti bosqich, olti xil nosozlik

Now the practical payoff. When a student tells me "the page won't load", that is not a diagnosis — it is a symptom, and it could be any of six completely different problems.

DNS failed: could not resolve host, the name has no address. TCP failed: connection refused or timed out, nothing is listening. TLS failed: a certificate warning — expired, wrong name, or an issuer your machine does not trust. The request was wrong: 404 for a path that does not exist, 405 for the right path with the wrong verb. The response failed: 500, which means your code raised an exception. Or everything succeeded and the page is blank — 200, HTML delivered, and your JavaScript threw an error on line four.

Six stages, six questions, six different fixes. Learning to say which stop failed is the single most useful habit in this module, and it is worth more than memorising any syntax I will show you.

Endi amaliy foydasi. Talaba menga "sahifa ochilmayapti" desa, bu tashxis emas — bu alomat, va u oltita butunlay boshqa muammodan biri bo'lishi mumkin.

DNS ishlamadi: hostni aniqlab bo'lmadi, nomning manzili yo'q. TCP ishlamadi: ulanish rad etildi yoki vaqt tugadi, hech kim tinglamayapti. TLS ishlamadi: sertifikat ogohlantirishi — muddati o'tgan, nomi noto'g'ri yoki ishonilmagan chiqaruvchi. So'rov noto'g'ri: mavjud bo'lmagan yo'l uchun 404, to'g'ri yo'l lekin noto'g'ri fe'l uchun 405. Javob muvaffaqiyatsiz: 500, ya'ni kodingiz xatolik chiqardi. Yoki hammasi muvaffaqiyatli o'tdi, lekin sahifa bo'sh — 200, HTML keldi, JavaScript esa to'rtinchi qatorda yiqildi.

Olti bosqich, olti savol, olti xil yechim. Qaysi bosqich ishlamaganini ayta olish — bu moduldagi eng foydali ko'nikma, va u men ko'rsatadigan har qanday sintaksisni yodlashdan qimmatroq.

09DNS

DNS: nomdan manzilga

Let us open the first stage. Computers route to numbers; people remember words. DNS is the distributed directory that converts one into the other.

It works in layers. First, cache — has this machine asked for that name recently? Usually yes, and we stop immediately, which is why the second visit to a site feels faster. If not, the question goes to a recursive resolver, typically your provider's, or a public one like 8.8.8.8. That resolver does the legwork.

It asks a root server, which says: I do not know udea dot uz, but here is who runs dot uz. It asks the TLD servers, which say: here are the authoritative name servers for udea dot uz. Finally the authoritative server answers: udea dot uz is 203.0.113.24, and you may keep that answer for three hundred seconds.

Nobody holds the whole directory. That is the point — it is distributed, which is why it has stayed up for forty years.

Birinchi bosqichni ochamiz. Kompyuterlar raqamlar bo'yicha yo'naltiradi, odamlar so'zlarni eslab qoladi. DNS — bu birini ikkinchisiga aylantiradigan taqsimlangan katalog.

U qatlamlar bilan ishlaydi. Avval kesh — bu kompyuter yaqinda shu nomni so'raganmi? Odatda ha, va shu yerda to'xtaymiz; saytga ikkinchi kirish shuning uchun tezroq tuyuladi. Agar yo'q bo'lsa, savol rekursiv resolverga boradi — odatda provayderingizniki yoki 8.8.8.8 kabi ochiq resolver. Asosiy ishni o'sha bajaradi.

U ildiz serverdan so'raydi, u aytadi: men udea nuqta uz'ni bilmayman, lekin nuqta uz'ni kim boshqarishini aytaman. TLD serverlaridan so'raydi, ular aytadi: mana udea nuqta uz uchun vakolatli nom serverlari. Nihoyat vakolatli server javob beradi: udea nuqta uz — bu 203.0.113.24, va bu javobni uch yuz soniya saqlab turishingiz mumkin.

Butun katalogni hech kim ushlab turmaydi. Gap ham shunda — u taqsimlangan, shuning uchun qirq yildan beri ishlab turibdi.

10Records · TTL

Yozuvlar va TTL

Four record types matter to you. An A record maps a name to an IPv4 address — that is what you will create in week twelve when you point a domain at your deployed Flask server. AAAA does the same for IPv6. CNAME points one name at another, which is how www follows the bare domain. MX points at a mail server, which you will need if your application sends registration emails.

And now the thing that wastes more student hours than anything else in this topic: TTL. When you change a DNS record and it "does not work yet", nothing is broken. The old answer is sitting in a cache somewhere between you and the root, and it will expire on its own schedule. You are not wrong — you are early. Wait for the TTL and check again.

Sizga to'rtta yozuv turi kerak bo'ladi. A yozuvi nomni IPv4 manziliga bog'laydi — o'n ikkinchi haftada domenni o'zingiz joylashtirgan Flask serveriga yo'naltirganda aynan shuni yaratasiz. AAAA xuddi shu ishni IPv6 uchun qiladi. CNAME bir nomni boshqasiga yo'naltiradi — www shu tarzda asosiy domenga ergashadi. MX pochta serveriga ko'rsatadi, ilovangiz ro'yxatdan o'tish xatlarini yuborsa kerak bo'ladi.

Endi bu mavzuda talabalarning eng ko'p vaqtini yeydigan narsa: TTL. DNS yozuvini o'zgartirganingizda u "hali ishlamayapti" bo'lsa, hech narsa buzilmagan. Eski javob siz bilan ildiz o'rtasidagi biror keshda turibdi va o'z muddati bo'yicha eskiradi. Siz xato qilmagansiz — erta keldingiz. TTL tugashini kuting va qayta tekshiring.

11Methods

HTTP metodlari

Stage four: the request. Every request carries a verb — the method — which tells the server what kind of thing you are asking for. Four matter to us now.

GET reads a resource. POST submits data and usually creates something. PUT replaces a resource entirely. DELETE removes it.

Two properties decide how you may use each one. Safe means the request changes nothing on the server. Because it changes nothing, a browser is free to fetch it, prefetch it, or retry it without asking anyone. Idempotent means sending it five times leaves the server in exactly the same state as sending it once.

Look at the table. GET is the only one of the four that is both. PUT and DELETE are idempotent but not safe — repeating them is harmless, but the first one already changed something. POST is neither, which is why your browser warns you before resubmitting a form.

To'rtinchi bosqich: so'rov. Har bir so'rov fe'lni — metodni — olib yuradi va serverga qanday narsa so'ralayotganini aytadi. Hozir bizga to'rttasi kerak.

GET resursni o'qiydi. POST ma'lumot yuboradi va odatda yangi narsa yaratadi. PUT resursni butunlay almashtiradi. DELETE uni o'chiradi.

Ikkita xususiyat ularning qanday ishlatilishini belgilaydi. Safe — so'rov serverda hech narsani o'zgartirmaydi. Hech narsa o'zgarmagani uchun brauzer uni hech kimdan so'ramasdan yuborishi, oldindan yuklashi yoki qayta yuborishi mumkin. Idempotent — uni besh marta yuborish serverni bir marta yuborgandagi holatda qoldiradi.

Jadvalga qarang. To'rttadan faqat GET ikkalasi ham. PUT va DELETE idempotent, lekin safe emas — takrorlash zararsiz, biroq birinchisi allaqachon o'zgartirgan. POST ikkalasi ham emas, shuning uchun brauzer formani qayta yuborishdan oldin ogohlantiradi.

12Security rule

Bu — uslub emas, xavfsizlik qoidasi

This is not academic tidiness. Look at the code on the screen: a delete link, written as an anchor tag with an id in the query string. It looks harmless. Many student projects contain exactly this.

An anchor tag produces a GET. And a GET, as we just said, is safe — which means everything on the internet that follows links feels entitled to fire it. A search engine crawler indexing your site. A chat application generating a link preview when someone shares the URL. The browser's own prefetcher, deciding to warm up a link you hovered over.

None of those is a human deciding to delete record seven. But record seven is gone, and your log shows a request nobody made.

Destructive actions go inside a POST form. We come back to this in week eleven, where the same mistake has a name — cross-site request forgery — and a whole lecture to itself.

One question while it is on screen: why is a password never sent with GET? [Take answers — browser history, server logs, the Referer header, someone reading over your shoulder. All four are correct.]

Bu akademik tozalik masalasi emas. Ekrandagi kodga qarang: o'chirish havolasi, query qatorida id bilan yozilgan anchor teg. Zararsiz ko'rinadi. Talabalar loyihalarining ko'pchiligida aynan shu bor.

Anchor teg GET hosil qiladi. GET esa, hozir aytganimizdek, safe — demak internetdagi havolalarga ergashadigan hamma narsa uni yuborishga haqli deb biladi. Saytingizni indekslayotgan qidiruv roboti. Kimdir havolani ulashganda ko'rinish yaratayotgan messenjer. Sichqonchani havola ustiga olib borganingizda uni oldindan yuklayotgan brauzerning o'zi.

Bularning hech biri yettinchi yozuvni o'chirishga qaror qilgan odam emas. Lekin yettinchi yozuv yo'q, va jurnalda hech kim yubormagan so'rov turibdi.

Buzuvchi amallar POST forma ichida bo'ladi. Bunga o'n birinchi haftada qaytamiz, u yerda shu xatoning nomi bor — cross-site request forgery — va unga butun bir ma'ruza ajratilgan.

Slayd ekranda turganda bitta savol: nega parol hech qachon GET bilan yuborilmaydi? [Javoblarni oling — brauzer tarixi, server jurnallari, Referer sarlavhasi, yelkangiz osha qarab turgan odam. To'rttasi ham to'g'ri.]

13Data placement

Ma'lumot qayerda ketadi

Same protocol, same server, completely different exposure. With GET, your data travels in the URL. It is visible in the address bar, stored in browser history, written into every server access log it passes through, and it can be bookmarked and shared by accident.

With POST, the data travels in the body. It is not in the address bar, not in history, not in the standard access log. It is not encrypted by that alone — TLS does the encrypting — but it is not sitting in plain sight either.

Practical rule for your coursework: filters, searches and page numbers go in a GET, because you want them bookmarkable. Anything a user typed about themselves goes in a POST.

Bir xil protokol, bir xil server, butunlay boshqacha ochiqlik. GET bilan ma'lumotingiz URL ichida yuradi. U manzil qatorida ko'rinadi, brauzer tarixida saqlanadi, yo'lda uchraydigan har bir server jurnaliga yoziladi va tasodifan xatcho'pga qo'shilib, ulashilib ketishi mumkin.

POST bilan ma'lumot tananing ichida yuradi. U manzil qatorida ham, tarixda ham, oddiy server jurnalida ham yo'q. Bu o'z-o'zidan shifrlash degani emas — shifrlashni TLS bajaradi — lekin ochiq ko'rinib ham turmaydi.

Kurs ishingiz uchun amaliy qoida: filtrlar, qidiruv va sahifa raqamlari GET'da bo'ladi, chunki ular xatcho'pga tushishi kerak. Foydalanuvchi o'zi haqida yozgan har qanday narsa POST'da bo'ladi.

14Status codes

Status kodlari

Stage five: the answer. Every response starts with a three-digit code, and the first digit tells you the whole story. One is informational, two is success, three is redirection, four means the client got it wrong, five means the server got it wrong.

That last distinction is the one to hold on to. Four hundred and something is your fault as the person making the request. Five hundred and something is the server admitting that it failed. When your own Flask app returns 500, you do not look at the browser — you look at the traceback in your terminal.

[Click through several codes.] Let me show you the ones you will actually meet. 200 — the default answer for a working page. 302 — what Flask sends after a successful form submission, when you redirect instead of re-rendering. 304 — your cached copy is still good, and if you see this while debugging CSS you are looking at an old file. 404 — no resource at this path, usually a typo in your route. 405 — the path exists but not for that verb; check the methods list on your route. 500 — you raised an exception. 502 — nginx reached your app and got nonsense back, which almost always means your Flask process is not running.

Beshinchi bosqich: javob. Har bir javob uch xonali kod bilan boshlanadi va birinchi raqam butun voqeani aytib beradi. Bir — axborot, ikki — muvaffaqiyat, uch — yo'naltirish, to'rt — mijoz xato qildi, besh — server xato qildi.

Oxirgi farqni yaxshi eslab qoling. To'rt yuzli kod — so'rov yuborgan odam sifatida sizning xatoyingiz. Besh yuzli kod — serverning o'zi muvaffaqiyatsizligini tan olishi. Flask ilovangiz 500 qaytarsa, brauzerga emas — terminalingizdagi traceback'ga qaraysiz.

[Bir nechta kodni bosib ko'rsating.] Amalda uchraydiganlarini ko'rsataman. 200 — ishlaydigan sahifaning odatiy javobi. 302 — formani muvaffaqiyatli yuborgandan keyin, qayta render qilish o'rniga redirect qilganingizda Flask yuboradigan kod. 304 — keshdagi nusxangiz hali yaroqli; CSS'ni tuzatayotganda buni ko'rsangiz, eski faylga qarab turibsiz. 404 — bu yo'lda resurs yo'q, odatda route'dagi imlo xatosi. 405 — yo'l bor, lekin bu fe'l uchun emas; route'dagi methods ro'yxatini tekshiring. 500 — siz xatolik chiqargansiz. 502 — nginx ilovangizga yetdi, lekin tushunarsiz javob oldi, bu deyarli har doim Flask jarayoni ishlamayotganini bildiradi.

15401 vs 403

401 va 403

Two codes that look similar and mean opposite things. This distinction is marked in your coursework, so I want it clear now rather than in week nine.

401, Unauthorized, means: I do not know who you are. No valid identity was presented. The correct response is to send the visitor to the login form.

403, Forbidden, means: I know exactly who you are, and you are not allowed here. The identity is fine; the permission is not.

The classic coursework bug is a logged-in student clicking an admin link and being bounced back to the login page. They log in again, successfully, click the link again, and get bounced again. That loop is what happens when you return 401 where you meant 403. A logged-in user who lacks permission should see a page that says so.

O'xshash ko'rinadigan, lekin qarama-qarshi ma'no anglatadigan ikki kod. Bu farq kurs ishida baholanadi, shuning uchun to'qqizinchi haftada emas, hozir aniq bo'lsin.

401, Unauthorized, degani: men sizning kimligingizni bilmayman. Haqiqiy shaxs taqdim etilmadi. To'g'ri javob — foydalanuvchini login formasiga yuborish.

403, Forbidden, degani: men sizning kim ekanligingizni aniq bilaman, va sizga bu yerga ruxsat yo'q. Shaxs joyida, ruxsat yo'q.

Klassik kurs ishi xatosi shunday: tizimga kirgan talaba admin havolasini bosadi va login sahifasiga qaytariladi. U qaytadan muvaffaqiyatli kiradi, havolani yana bosadi va yana qaytariladi. Bu halqa — 403 kerak bo'lgan joyda 401 qaytarganingizda yuz beradi. Ruxsati yo'q, lekin tizimga kirgan foydalanuvchi shu haqda yozilgan sahifani ko'rishi kerak.

17Five headers

Beshta muhim sarlavha

Five you will meet personally this semester. Host: one IP address can serve hundreds of domains, and this header is how the server tells them apart — exactly the mechanism behind nginx virtual hosts in week eight.

Content-Type: get it wrong and the browser displays your HTML as plain text, or refuses your JSON. Every year somebody spends an afternoon on this.

Cookie and Set-Cookie: how a protocol with no memory remembers that you logged in. Weeks nine and eleven.

Cache-Control: the reason your CSS edit "did not apply". Hard-refresh before you start rewriting selectors.

Strict-Transport-Security: tells the browser to refuse plain HTTP for this domain in future. You will set this in week twelve.

Bu semestrda shaxsan uchrashadiganingiz beshta. Host: bitta IP manzil yuzlab domenga xizmat qilishi mumkin, va server ularni shu sarlavha orqali ajratadi — sakkizinchi haftadagi nginx virtual hostlarining aynan shu mexanizmi.

Content-Type: buni noto'g'ri qo'ysangiz, brauzer HTML'ingizni oddiy matn sifatida ko'rsatadi yoki JSON'ingizni qabul qilmaydi. Har yili kimdir shunga yarim kun sarflaydi.

Cookie va Set-Cookie: xotirasi yo'q protokol sizning tizimga kirganingizni shu orqali eslab qoladi. To'qqizinchi va o'n birinchi haftalar.

Cache-Control: CSS o'zgarishingiz "ishlamagani" ning sababi. Selektorlarni qayta yozishdan oldin qattiq yangilang.

Strict-Transport-Security: brauzerga bu domen uchun kelajakda oddiy HTTP'ni rad etishni aytadi. Buni o'n ikkinchi haftada o'rnatasiz.

18HTTPS

Qulf nimaga kafolat beradi

HTTPS is simply HTTP carried inside TLS. It gives you three guarantees, and it withholds a fourth that almost everyone assumes.

Confidentiality: nobody between you and the server can read the traffic. Integrity: nobody can alter it in transit without being detected. Authentication: the server proved that it holds the private key for that domain name.

And here is what it does not guarantee — that the site is honest. A phishing site can hold a perfectly valid certificate. Certificates are free and issued in seconds; proving you control a domain is not the same as proving you are trustworthy.

This matters because you will build sites that ordinary people use, and those people have been told "look for the padlock". That advice is incomplete, and now you know why.

HTTPS — bu shunchaki TLS ichida yuradigan HTTP. U uchta kafolat beradi va deyarli hamma o'ylaydigan to'rtinchisini bermaydi.

Maxfiylik: siz bilan server o'rtasidagi hech kim trafikni o'qiy olmaydi. Yaxlitlik: hech kim uni yo'lda sezdirmasdan o'zgartira olmaydi. Autentifikatsiya: server o'sha domen nomining maxfiy kalitiga egaligini isbotladi.

Va u kafolatlamaydigan narsa — saytning halolligi. Fishing sayti mukammal amaldagi sertifikatga ega bo'lishi mumkin. Sertifikatlar bepul va bir necha soniyada beriladi; domenni boshqarishni isbotlash ishonchli ekanligingizni isbotlash emas.

Bu muhim, chunki siz oddiy odamlar ishlatadigan saytlar quryapsiz, va o'sha odamlarga "qulf belgisiga qarang" deb o'rgatilgan. Bu maslahat to'liq emas, va endi siz sababini bilasiz.

19Handshake

TLS handshake

Four steps, and you only need the shape of it. The client says hello and lists the cipher suites it supports. The server replies with its choice and sends its certificate chain. The client checks that chain against the root certificates that shipped with your operating system, and checks that the name matches and the dates are valid. Then both sides derive a shared session key, and from that point the connection is encrypted with fast symmetric cryptography.

Notice where trust actually lives: in the root certificates on your machine. If a root were removed from your trust store, the site would start showing warnings — and nothing about the server would have changed. Trust is a property of your configuration, not of the remote site. That is one of the seminar questions today.

In week twelve you will put your own Flask application behind nginx with a Let's Encrypt certificate. It costs nothing, and a login form served over plain HTTP loses marks under the security criterion.

To'rt qadam, va sizga uning umumiy shakli yetarli. Mijoz salom beradi va qo'llab-quvvatlaydigan shifrlash to'plamlarini sanaydi. Server tanlovini aytadi va sertifikat zanjirini yuboradi. Mijoz o'sha zanjirni operatsion tizimingiz bilan kelgan ildiz sertifikatlariga solishtiradi, nom mosligini va muddatini tekshiradi. Keyin ikki tomon umumiy sessiya kalitini hosil qiladi va shundan boshlab ulanish tez simmetrik shifrlash bilan himoyalanadi.

Ishonch aslida qayerda yashashiga e'tibor bering: kompyuteringizdagi ildiz sertifikatlarida. Agar ildiz sertifikat ishonch ro'yxatidan olib tashlansa, sayt ogohlantirish ko'rsata boshlaydi — serverda esa hech narsa o'zgarmagan bo'ladi. Ishonch — bu sizning sozlamangizning xususiyati, uzoqdagi saytning emas. Bu bugungi seminar savollaridan biri.

O'n ikkinchi haftada o'z Flask ilovangizni Let's Encrypt sertifikati bilan nginx ortiga qo'yasiz. Bu bepul, va oddiy HTTP orqali ishlaydigan login formasi xavfsizlik mezoni bo'yicha ball yo'qotadi.

20Instruments

To'rtta asbob

You will spend far more time reading requests than writing them. Four instruments, and each answers a different question — that is the point, not the commands themselves.

Ping asks: is the host reachable at all? Nslookup asks: what address does this name resolve to? Curl asks: what exactly did the server send back, byte for byte, with no browser in the way? And the DevTools Network panel asks: what did the browser request, in what order, and how long did each one take?

One warning. On many managed networks — including some of ours — ping is blocked, so a failed ping does not mean the host is down. If that happens, use curl instead. A student who concludes their laptop is broken because ping failed has diagnosed the wrong stage.

Siz so'rovlarni yozishdan ko'ra ularni o'qishga ancha ko'p vaqt sarflaysiz. To'rtta asbob, va har biri boshqa savolga javob beradi — gap buyruqlarning o'zida emas, aynan shunda.

Ping so'raydi: host umuman yetib borarlimi? Nslookup so'raydi: bu nom qaysi manzilga aylanadi? Curl so'raydi: server aslida nima yubordi, brauzer aralashuvisiz, bayt-baytiga? DevTools Network paneli esa so'raydi: brauzer nimalarni, qanday tartibda so'radi va har biri qancha vaqt oldi?

Bitta ogohlantirish. Ko'plab boshqariladigan tarmoqlarda — shu jumladan bizning ba'zi tarmoqlarimizda — ping bloklangan, shuning uchun ping ishlamagani host o'chgan degani emas. Bunday holda curl ishlating. Ping ishlamagani uchun noutbugim buzilibdi deb xulosa qilgan talaba noto'g'ri bosqichni tashxis qilgan bo'ladi.

21Reading responses

Javobni brauzersiz o'qish

23Git

Git bir daqiqada

Five commands, and three ideas behind them. Git init starts tracking a folder. Git add stages a change. Git commit records it permanently with a message explaining why. Git remote add points at GitHub, and git push uploads.

The three ideas matter more than the commands. The working directory is what you just edited. The staging area is what you have chosen to include in the next commit — and you will not always want everything. The repository is the permanent history. Add moves work from the first to the second; commit moves it from the second to the third.

Most beginners treat add and commit as one step. Once you understand the staging area, you can commit one logical change at a time instead of dumping an afternoon's work into a single entry.

We are not doing branches today — those arrive in week four. Today's goal is narrow: everyone leaves the seminar with a repository containing a commit they made themselves.

Beshta buyruq va ular ortidagi uchta g'oya. Git init papkani kuzatishni boshlaydi. Git add o'zgarishni sahnaga qo'yadi. Git commit uni sababi bilan doimiy yozib qo'yadi. Git remote add GitHub'ga ko'rsatadi, git push esa yuklaydi.

Uchta g'oya buyruqlardan muhimroq. Working directory — hozir tahrirlaganingiz. Staging area — keyingi commit'ga qo'shishni tanlaganingiz, va siz har doim hamma narsani qo'shishni xohlamaysiz. Repository — doimiy tarix. Add ishni birinchisidan ikkinchisiga ko'chiradi, commit ikkinchisidan uchinchisiga.

Ko'p boshlovchilar add va commit'ni bitta qadam deb biladi. Staging area'ni tushunganingizda, yarim kunlik ishni bitta yozuvga tiqish o'rniga, bir vaqtda bitta mantiqiy o'zgarishni commit qila olasiz.

Bugun branch'lar bilan ishlamaymiz — ular to'rtinchi haftada keladi. Bugungi maqsad tor: har bir talaba seminardan o'zi qilgan commit'i bo'lgan repozitoriy bilan chiqadi.

24Commit messages
